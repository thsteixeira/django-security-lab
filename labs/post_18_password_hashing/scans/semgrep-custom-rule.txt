          ❰❰ Blocking ❱❱
          A password is stored, or checked, as a digest computed with hashlib or hmac rather than through     
          Django's hasher. A general-purpose hash is built to be fast, so once the table leaks every guess    
          costs one hash; without a per-row salt the same password gives the same value in every row, and each
          guess is checked against all of them at once. The algorithm is not the problem: SHA-256 or BLAKE2   
          fail the same way as SHA-1. Store passwords with user.set_password() (or make_password()), which    
          uses the first entry of PASSWORD_HASHERS, a per-row salt and a work factor, and check them with     
          user.check_password(). Rows already stored this way can be wrapped in PBKDF2 by a data migration    
          without knowing a password, but a table that has already leaked is cracked anyway: reset those      
          passwords.
